Glosario

ACL. Acrónimo de Access Control List (“lista de control de acceso”). Es un mecanismo que permite extender los permisos que ofrece un sistema operativo.

DoS. Acrónimo de Denial of Service (“denegación de servicio”). Ataque informático cuyo fin es el bloqueo de un servidor mediante la saturación del mismo o mediante explotación de alguna vulnerabilidad que consiga el mismo resultado.

EBCDIC. Acrónimo de Extended Binary Coded Decimal Interchange Code (“código de intercambio decimal codificado en binario extendido”). Código binario empleado para representar caracteres alfanuméricos, controles y signos de puntuación.

GID. Abreviatura de Group Identifier (“identificador de grupo”). Cadena numérica o alfanumérica que permite identificar al grupo de un sistema entre los demás.

GPL. Acrónimo de General Public License (“Licencia Pública General de GNU”). Licencia muy utilizada en software libre de código abierto que garantiza la libertad de uso, estudio, copia y modificación del software.

LDAP. Acrónimo de Lightweight Directory Access Protocol (“protocolo ligero de acceso a directorios”). Es un conjunto de protocolos abiertos usados para acceder a información a través de la red.

Mirrors. Réplicas de un servidor ubicadas en diferentes ubicaciones físicas.

PROM. Acrónimo de Programmable Read Only Memory (“memoria programable de solo lectura”). Tipo de memoria empleado en dispositivos electrónicos digitales para almacenar programas de bajo nivel que no deben borrarse.

SSL. Acrónimo de Secure Sockets Layer (“capa de sockets seguros”). Es una tecnología que mantiene seguras las conexiones a través de Internet mediante algoritmos de cifrado que codifican los datos.

TLS. Acrónimo de Transport Layer Security (“seguridad en la capa de transporte”). Versión actualizada y más segura de SSL.

UID. Abreviatura de User Identifier (“identificador de usuario”). Cadena numérica o alfanumérica que permite identificar al usuario de un sistema entre los demás.

Virgulilla. Signo ortográfico con forma de coma, rasguillo o trazo, que en sistemas operativos UNIX/Linux se corresponde con el directorio home del cliente autenticado.

4.1. Introducción

Como su propio nombre indica, los servicios de transferencia de ficheros tienen como objetivo la transferencia de ficheros que residen en un equipo a otra ubicación física. Este tipo de servicios ofrece ventajas frente a otras alternativas (envío de información como adjuntos de correo electrónico, transporte físico en soportes de almacenamiento externos…), pues se han diseñado por y para este fin.

4.2. Protocolo FTP

El protocolo FTP (File Transfer Protocol o protocolo de transferencia de ficheros) es un protocolo de aplicación encargado de transferir ficheros entre nodos. Desde sus orígenes en 1971, cuando se publicó la primera especificación en la RFC 114, ha estado presente en infinidad de entornos y se ha usado ampliamente para la administración de carpetas remotas y el intercambio de ficheros. Opera en la capa de aplicación de la pila de protocolos TCP/IP y trabaja sobre el protocolo TCP de la capa de transporte. La versión actual del protocolo está descrita en la RFC 959.

Para saber más

La mayor parte de los servidores que ofrecían hosting web permitían la administración de los sitios a través de FTP. Otros escenarios en los que este protocolo se utilizaba frecuentemente eran los numerosos mirrors desde los que se descargaba software, repositorios de distribuciones Linux, por ejemplo, o dispositivos que permiten actualizaciones de su firmware a través de la red (medidores de potencia, routers, impresoras…).

4.2.1. Características y funcionamiento

A pesar de su nombre, FTP ofrece más posibilidades a la hora de interactuar con el sistema de archivos remoto que la simple transferencia: crear directorios, eliminar o renombrar ficheros y directorios, obtener un listado del contenido del directorio…

Figura 4.2 Esquema de trabajo FTP.

El servidor FTP puede trabajar en modo activo o pasivo, pero en cualquier caso siempre permanece a la escucha de solicitudes de conexión por el puerto 21, que es el predeterminado

(en apartados posteriores se detallan estos modos de conexión). En ese puerto se establecerá la conexión de control por la que el cliente enviará comandos y el servidor las respuestas. De forma paralela, por cada comando enviado por la conexión de control se irán creando las conexiones para datos por las que se realizarán las transferencias. En la figura 4.2 se muestra el esquema general de funcionamiento del protocolo FTP y a continuación se describe cada uno de los agentes implicados en la comunicación:

● Interfaz de usuario: Aplicación o conjunto de comandos de alto nivel que permiten al usuario interactuar con el PI cliente para que envíe comandos FTP al PI servidor.

● PI (Protocol Interpreter o intérprete del protocolo):

– Cliente: Proceso que establece la conexión con el PI servidor, emite los comandos FTP y recibe las respuestas y controla el DTP cliente. – Servidor: Proceso que permanece a la escucha de conexión por parte del PI cliente, recibe comandos FTP, emite respuestas y controla el DTP servidor.

● DTP (Data Transfer Process o proceso de transferencia de datos):

– Cliente: Proceso que espera a que el DTP servidor inicie la conexión al puerto de datos especificado para realizar la transferencia. Si el modo de trabajo es pasivo, en vez de esperar la conexión, la inicia. – Servidor: Proceso que establece una conexión con el DTP cliente para realizar la transferencia. Si el modo de trabajo es pasivo, en vez de iniciar la conexión, espera a recibirla.

FTP se diseñó para realizar transferencias con la máxima velocidad añadiendo la menor cantidad de información posible a las cabeceras de los paquetes. Este diseño no tuvo en cuenta aspectos de seguridad, lo cual hace que sea un protocolo inseguro, pues todo el tráfico (incluido el empleado en establecer la sesión) viaja sin cifrar (incluidos los datos empleados para el establecimiento de la sesión). Es por ello por lo que puede necesitar de mecanismos extra de seguridad para seguir siendo aplicable en según qué entornos (capa extra SSL/TLS).

Investiga

Existe una variante del protocolo denominada FXP (File eXchange Protocol) que permite optimizar la transferencias entre dos servidores. Busca información sobre ella y elabora un diagrama que represente su modo de trabajo.

4.2.2. Tipos de conexión

Una vez que el cliente ha establecido la conexión de control con el servidor, cada vez que envíe un comando que implique transferencia de información se creará una conexión para

datos (quedan excluidos comandos que ejecutan tareas que no transfieren datos masivos como eliminación de ficheros, creación de directorios…). Quién inicia las conexiones de datos, así como los puertos seleccionados para ellas, son dos cuestiones que dependen directamente del modo de conexión empleado.

A)  Conexión modo activo

Es el modo predeterminado. Los pasos seguidos para establecer las conexiones en modo activo son:

1. El cliente selecciona la dirección y el puerto activo (este último, superior a 1023) por donde esperará que le llegue la petición de inicio de conexión para datos y se lo comunica al servidor mediante el comando PORT. 2. El servidor responde con el mensaje de confirmación a través de la conexión de control. 3. El cliente envía el comando correspondiente al servidor por la conexión de control. 4. El servidor envía una respuesta preliminar positiva por la conexión de control. 5. A continuación, el servidor inicia una conexión para datos desde su puerto 20 al puerto que el cliente le notificó en el comando PORT y se realiza la transferencia. 6. Una vez finaliza la transferencia, el servidor responde con el mensaje de finalización correspondiente a través del canal de control.

Este modo de trabajo implica que el equipo cliente debe aceptar conexiones entrantes en puertos superiores a 1023, lo que genera un problema de seguridad. Por ello, en la mayor parte de las ocasiones es preciso emplear conexiones en modo pasivo.

B)  Conexión modo pasivo

Dada la problemática asociada a la seguridad del modo activo, el modo pasivo propone que sea el servidor el que asuma la responsabilidad de admitir las conexiones para datos. Los pasos seguidos para establecer las conexiones en modo pasivo son:

1. El cliente envía un comando PASV por el canal de control al servidor. 2. El servidor selecciona un puerto (superior a 1023) y se lo notifica al cliente FTP en la respuesta de confirmación para que este sepa donde deberá iniciar la conexión de datos. 3. El cliente envía el comando correspondiente al servidor por la conexión de control. 4. El servidor envía una respuesta preliminar positiva por la conexión de control. 5. El cliente selecciona un puerto local (superior a 1023), inicia la conexión de datos desde ese puerto hacia el puerto que le indicó el servidor como respuesta al comando PASV y se realiza la transferencia. 6. Una vez finaliza la transferencia, el servidor responde con el mensaje de finalización correspondiente a través del canal de control.

Toma nota

En este modo de trabajo, el puerto 20 del servidor no se utiliza.

4.2.4. Usuarios y grupos. Acceso anónimo

Independientemente del modo de trabajo, así como de la tarea para realizar, el protocolo requiere del establecimiento de una sesión, para lo cual es necesario proporcionar credenciales de acceso (usuario y password). Una vez el usuario ha establecido una sesión válida, dispone de acceso al directorio remoto y podrá llevar a cabo sobre él las acciones que su rol de usuario le permita. Este acceso puede ser de diferente tipo dependiendo de la versión del servidor, así como de la configuración de este:

a) Acceso a un usuario autorizado: El cliente emplea sus credenciales de usuario que se han registrado anteriormente en el servidor. Estas pueden, o bien coincidir con las de un usuario real (una cuenta de equipo local o una cuenta de dominio), o bien residir en otros almacenes de datos (bases de datos, LDAP, ficheros de texto…). Cabe destacar que,

al igual que ocurre con la gestión de sistemas operativos, la concesión de permisos y el establecimiento de configuraciones de forma individualizada a cada usuario pueden ser una labor tediosa si existe un número elevado de usuarios. Es por ello por lo que algunos servidores permiten realizar una gestión de usuarios basada en grupos, mediante la cual se pueden establecer unas configuraciones generales que afectarán a todo usuario miembro del grupo. b) Acceso anónimo: El cliente utiliza como login “anonymous” y como password, normalmente, una dirección de correo electrónico.

4.2.5. Permisos, cuotas y límite de ancho de banda

Permitir conexiones remotas a un directorio entraña ciertos riesgos de privacidad, pero si, además, este acceso ofrece la posibilidad de modificar la información de los contenidos del directorio, el riesgo es aún mayor. Por ello, de manera análoga a como se hace en un sistema operativo, se deben especificar los permisos que un usuario/grupo tiene para trabajar sobre el directorio remoto. Hay que tener en cuenta que el establecimiento de estos permisos depende en gran medida del tipo de servidor y que siempre estarán supeditados a los permisos locales. Asimismo, es recomendable configurar el tamaño máximo de espacio que podrá ocuparse mediante el establecimiento de cuotas. No solamente se debe tener en cuenta el peligro que entraña desbordar el espacio de almacenamiento del servidor. También debe prestarse atención a los límites de subida y bajada establecidos, así como al número máximo de usuarios simultáneos, pues, de lo contrario, se puede producir fácilmente una situación similar a la de un ataque DoS. En cualquier caso, los límites de subida y bajada también se verán afectados por el ancho de banda disponible, el cual puede depender de varios factores (acceso desde red local o desde el exterior, velocidad contratada, estado de saturación de la red…).

4.2.6. Modos de transferencia

Conforme a la especificación del protocolo, las transferencias FTP pueden llevarse a cabo de diferentes maneras según el tipo de dato especificado, indicando que pueden utilizarse tipos de datos ASCII, Binary (Image) y EBCDIC. Sin embargo, generalmente solo se implementan los tipos ASCII y Binary:

• ASCII: Se debe usar para transferencias de archivos de texto plano (.txt, .html, .php…). Es importante aclarar que FTP con este modo de transferencia representa el final de línea con los caracteres CRLF, al igual que Microsoft. Sin embargo, los equipos basados en UNIX lo representan con LF y algunos otros con CR. Esta circunstancia obliga a que, cuando los archivos de texto llegan a la plataforma destino, en algunos casos se deban adaptar los finales de línea. Estas adaptaciones para finales de línea no son adecuadas para ficheros binarios, motivo por el cual una transferencia de ficheros de este tipo en modo ASCII puede dar lugar a archivos corruptos tras la descarga. • Binary: Debe emplearse para transferir archivos de tipo binario (.jpg, .exe, .mp3…).

No obstante lo anterior, muchos clientes FTP establecen el modo de transferencia de forma automática conforme al tipo de fichero que enviar.

4.3. Protocolo FTPS

Una de las debilidades del protocolo FTP es la seguridad. El hecho de que las comunicaciones viajen en claro, incluso cuando se están intercambiando usuario y password para iniciar la sesión, hace que sea muy vulnerable. Para paliar estas limitaciones se puede hacer uso de FTPS (FTP Secure). Esta extensión de FTP cifra las comunicaciones mediante protocolos de cifrado SSL/TLS haciendo que la comunicación sea segura. Existen dos métodos:

1. Implícito o FTPS: Funciona de manera similar a HTTPS. La seguridad se habilita con SSL tan pronto como se inicia la conexión. El puerto predeterminado es el 990. Este protocolo fue la primera versión de FTP encriptado y, aunque se considera obsoleta, todavía se usa ampliamente. 2. Explícito o FTPES: La comunicación comienza como con FTP simple a través del puerto 21, pero a través de comandos FTP especiales se actualiza al cifrado SSL/TLS. Esta actualización normalmente se hace antes de que se envíen las credenciales de usuario. Es el método preferido.

Para saber más

– Ninguno de los principales navegadores web admite FTPS ni FTPES. – Otra alternativa al FTP tradicional es SFTP (Secure File Transfer Protocol o protocolo seguro de transferencia de archivos). SFTP, a diferencia de FTPS/FTPES, no es una adaptación del protocolo FTP para que trabaje de forma segura sobre SSL/TLS, sino una implementación nueva que se ejecuta sobre SSH y que por defecto emplea el puerto 22.

Investiga

Las soluciones basadas en SSL/TLS requieren de un certificado digital para hacer seguras las conexiones. Averigua cómo obtener un certificado digital válido para poderlo utilizar en tu servidor FTP.

4.4. Protocolo TFTP

El protocolo TFTP (Trivial File Transfer Protocol o protocolo de transferencia de ficheros trivial) es un protocolo de aplicación que, junto con BOOTP, se encarga de permitir el arranque de máquinas sin disco en una red local. Está descrito en la RFC 1350.

Figura 4.4 TFTP y su enclave en el modelo TCP/IP.

Entre las características principales de este protocolo se encuentran:

• Es un protocolo sencillo y sin autenticación, por lo que no se produce intercambio de usuario ni password. • La implementación del protocolo es de reducido tamaño (normalmente va grabado en memorias PROM). • Trabaja sobre UDP (puerto 69). Al implementarse sobre UDP, debe ser el propio protocolo TFTP el que maneje la pérdida y duplicado de paquetes. • Actualmente existen tres modos de transferencia:

– NetASCII: Utiliza caracteres ASCII de 8 bits. Un cliente que recibe datos en modo NetASCII debe traducirlos a su propio formato. – Octet: Trata los datos como bytes de 8 bits sin interpretación. – Mail: Definido en el RFC 783, actualmente está obsoleto según la propia RFC 1350.

B)  Configuración

a) Creación de las cuentas de usuario

La configuración del servicio se lleva a cabo desde el fichero de texto plano /etc/proftpd/ proftpd.conf, que será analizado por el demonio proftpd. Este fichero contendrá las directivas de configuración contenidas en diferentes secciones, pero no es necesario especificar todas las directivas, pues el servidor dispondrá de una configuración predeterminada.

Primeramente, se deben crear los grupos de usuarios:

$ sudo groupadd Informaticos $ sudo groupadd Contables

Antes de dar de alta los usuarios, es conveniente tener en cuenta si estos accederán en algún momento al servidor por otras vías (conexiones remotas, acceso físico…), si en algún momento se desea que cada usuario tenga su directorio personal o si, por el contrario, los accesos se realizarán únicamente a través de FTP. Si se trata de este último caso, el cual coincide con el de los escenarios propuestos, se puede tener en consideración a la hora de crear las cuentas de usuario para añadir algo de seguridad. A continuación se crean las cuentas de usuario sin que se creen grupos con el mismo nombre (opción “-N”), haciendo que sus grupos principales sean los creados anteriormente (en el caso de los usuarios contables e informáticos con la opción “-g”), sin directorio personal (opción “-M”) e indicando que no tienen posibilidad de iniciar sesión de forma interactiva (opción “-s”):

$ sudo useradd AdminFTP -s /bin/false -M -N $ sudo useradd Informatico1 -s /bin/false -g Informaticos -M -N $ sudo useradd Informatico2 -s /bin/false -g Informaticos -M -N $ sudo useradd Contable1 -s /bin/false -g Contables -M -N $ sudo useradd Contable2 -s /bin/false -g Contables -M -N

$ sudo passwd AdminFTP $ sudo passwd Informatico1 $ sudo passwd Informatico2 $ sudo passwd Contable1 $ sudo passwd Contable2

b) Configuración escenario: EJEMPLO LOCAL

El fichero de configuración posee las siguientes características:

● Permite la inserción de tabulaciones y líneas adicionales para su formateo.

● Permite la inclusión de comentarios. Deben ir precedidos por el carácter almohadilla (#) y terminan al final de la línea.

● Las directivas incluidas en él son case-insensitive.

● Cada directiva tiene una sintaxis de especificación (clave valor) y un valor predeterminado, y debe especificarse en un determinado contexto (ver cuadro 4.6).

Cuadro 4.6 Tipos de contexto

Define la directiva para el servidor principal.

Fichero proftpd.conf

<VirtualHost> Crea un conjunto de directivas de configuración que se aplican a un nombre de host o dirección IP en particular (se utiliza para crear un servidor virtual).

<Global> Engloba un conjunto de directivas de configuración que se aplican al servidor principal y al resto de servidores virtuales (secciones <VirtualHost>).

<Anonymous> Detalla la configuración de inicio de sesión anónimo. Por defecto se establece en el directorio ~ftp (que se mapea a /srv/ftp por ser este el directorio home del usuario ftp).

<Limit> Establece qué usarios/grupos pueden usar qué comandos FTP. Su configuración es compleja. Algunos de los comandos aquí especificados dependen en última instancia de los permisos del sistema de archivos subyacente. Algunos de los grupos de comandos que se pueden emplear son:

● LOGIN: Se corresponde con los comandos de inicio de sesión.

● DIRS: Engloba los comandos de manejo de directorios.

● WRITE: Agrupa comandos que producen algún cambio sobre el sistema de archivos (crear ficheros, borrar directorios…).

● READ: Son operaciones de lectura.

<Directory> Engloba las directivas de configuración que se aplican al directorio especificado y sus subdirectorios. Se puede agregar una barra inclinada y un asterisco (“/*”) a la ruta para indicar que la configuración se aplica solo a los contenidos y sub-contenidos, no al directorio en sí. Si contiene el carácter virgulilla (~), este se sustituye por su directorio home en el momento en que el cliente se autentica.

Pero antes de realizar la configuración del servidor para el escenario EJEMPLO LOCAL, se deben crear los directorios que serán servidos por FTP. La configuración de los permisos y propietarios debe permitir que el usuario que se conecte de forma remota pueda realizar en él las acciones requeridas. Sin entrar en detalle en soluciones basadas en ACL, y como solución válida para los escenarios propuestos, se sugiere la siguiente configuración:

$ sudo mkdir /EJEMPLO_LOCAL $ sudo chmod 777 /EJEMPLO_LOCAL

Para configurar el servidor conforme a los requisitos de acceso indicados, se establecerán las siguientes directivas en el fichero de configuración /etc/proftpd/proftpd.conf:

ServerName "Servidor Escenario EJEMPLO LOCAL" ServerType standalone DefaultServer on Port 21

Umask 000 MaxInstances 50 User proftpd Group nogroup DefaultRoot /EJEMPLO_LOCAL RequireValidShell off

<Limit LOGIN> AllowUser AdminFTP AllowGroup OR Informaticos,Contables DenyAll </Limit>

<Directory /EJEMPLO_LOCAL> <Limit READ WRITE DIRS> DenyAll </Limit> <Limit READ DIRS> AllowGroup Contables </Limit> <Limit READ WRITE DIRS> AllowUser AdminFTP AllowGroup Informaticos </Limit> AllowOverwrite on </Directory>

En donde:

● ServerName: Es el texto mostrado a los clientes que se conectan al servidor.

● ServerType: Indica si el servidor se ejecuta desde inetd o en modo standalone (independiente). Si va a ser un servidor dedicado que atienda un elevado número de conexiones, será conveniente seleccionar standalone.

● DefaultServer: Indica, en caso de habilitarse, que ante peticiones que llegan al servidor pero que no van a la dirección principal ni a la de un host virtual se tome la configuración del servidor como configuración de respaldo.

● Port: Establece el número de puerto para conexiones de control.

● Umask: Especifica la máscara de usuario que finalmente determina los permisos con los que se crean los ficheros y directorios. En escenarios en los que todos los usuarios deben tener control sobre los contenidos de los demás, se establece a 000 (por defecto es 022).

● MaxInstances: Establece el número máximo de procesos secundarios (conexiones) que puede generar el proceso proftpd (se ignora con ServerType inetd).

● User y Group: Establecen el UID y GID bajo los que se ejecutará ProFTPD. Por defecto, ProFTPD se ejecuta como usuario root, lo cual es altamente peligroso.

● DefaultRoot: Indica el directorio bajo el cual se encerrará al cliente (será su directorio raíz).

● RequireValidShell: Permite o deniega inicios de sesión para usuarios que no tienen un shell incluido en /etc/shells.

● AllowUser y AllowGroup: Especifican los nombres de usuario y grupo que pueden acceder a la sección mediante expresiones lógicas formadas por un operador lógico (AND, OR) seguido de una lista de nombres separados por comas (“,”). Se admite que cada nombre del listado esté prefijado con el operador de negación “!”, indicándose así todos los no coincidentes con nombre. De forma predeterminada, AllowUser ya se evalúa como una lista booleana OR, por lo que no es necesario anteponer el operador OR. Estas directivas también permiten evaluar expresiones como expresiones regulares con el operador regex.

● AllowAll y DenyAll: Permite o deniega, respectivamente, el acceso a la sección.

● AllowOverwrite: Establece si los archivos pueden o no sobrescribirse (por defecto, los clientes ftp no pueden sobrescribir archivos existentes).

En el segundo escenario se deben permitir accesos anónimos de lectura, así como accesos de lectura y escritura para el usuario AdminFTP. <Anonymous /EJEMPLO_NET> User ftp Group nogroup UserAlias anonymous ftp DirFakeUser on ftp DirFakeGroup on ftp MaxClients 10 DisplayLogin welcome.msg DisplayChdir .message

<Limit LOGIN> AllowAll </Limit>

En donde:

● UserAlias: Nombre adicional para inicio de sesión.

● DirFakeUser y DirFakeGroup: Permiten ocultar los usuarios y grupos reales de los archivos de un directorio. Si se activa, mostrará todos los archivos como propiedad del usuario, o grupo, “ftp”, aunque se puede incluir también un nombre de usuario para especificar un usuario distinto (el nombre de grupo o nombre de usuario especificado no necesita existir).

Debe tomar un valor inferior al de MaxInstances para que los clientes reciban un mensaje de error cuando sean rechazados. También admite none para eliminar todos los límites máximos de conexión del contexto de configuración aplicable.

● DisplayLogin y DisplayChdir: Indican el archivo de texto plano que se mostrará al usuario cuando inicie sesión o cambie a un directorio.

Resumen

n FTP es un protocolo que se diseñó para transferir ficheros con la mayor velocidad, pero que no tiene en cuenta la seguridad, pues todo el tráfico viaja en claro. n Los clientes FTP deben enviar su login y password, aunque se permiten accesos anónimos. Estos disponen de un amplio repertorio de comandos. n La comunicación puede llevarse a cabo en modo activo o pasivo. n El servidor mantiene un canal de control para el intercambio de comandos y sus respuestas (formadas por un código de estado y un mensaje informativo). A través de este canal se intercambia la información necesaria para establecer las conexiones de datos e iniciar las transferencias. n Cada cuenta de usuario, incluso si se trata del usuario anónimo, accederá a un directorio remoto del servidor con unos permisos determinados. Estos permisos serán proporcionados por las directivas de acceso del servicio, así como por los permisos propios del sistema de archivos.

n Dependiendo del tipo de contenido para transferir, puede ser conveniente modificar el tipo de transferencia. n TFTP es un protocolo simple de transferencia de ficheros que se utiliza conjuntamente con BOOTP para permitir el arranque de máquinas a través de la red. n FTPS o SFTP son alternativas que ofrecen seguridad.
